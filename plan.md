# Staff-Facing Heatmap Implementation Plan

## Context

The current app is a **fan-facing** simulation tool: it replays historical POS transactions from JSON files through a `SimulationEngine`, producing a `HeatState` (normalized 0-1 per location) that colors 6 concession nodes on an SVG arena map. The call confirmed **real-time data** is the target, not historical replay. This plan mocks the staff view using the existing simulation as a stand-in data source, so we can validate the UX before Mark builds the real ingestion layer.

**Note for Mark:** The architecture needs a WebSocket-based ingestion service that normalizes POS webhooks + sensor data into the same `HeatState` shape the frontend already consumes. The `SimulationEngine` gets swapped for a `LiveDataEngine` subscriber — everything downstream stays the same.

---

## Step 1: Define new types for staff-view data model

**File:** `src/lib/types.ts`

Add interfaces that extend the existing data model with staff-specific fields:

- `StaffHeatState` — extends `HeatState` with per-location `waitMinutes`, `queueDepth`, and `alertLevel` fields
- `StandAlert` — `{ locationId, severity: 'warning' | 'critical', message, timestamp }`
- `ConcourseFlow` — `{ fromSection, toSection, intensity: number }` for directional foot traffic
- `StaffViewState` — composite type bundling `StaffHeatState`, active alerts, flow data, and game clock info

This keeps the existing `HeatState` interface untouched so the fan view still works.

## Step 2: Build mock data derivation layer

**File:** `src/lib/staffMock.ts` (new)

A pure function that takes the existing `SimulationEngine` output (`HeatState` + `SimulationStats`) and derives mock staff data:

- `waitMinutes` per location: derived from heat value (`Math.round(heat * 10)`, capped at 12)
- `queueDepth` per location: derived from heat + random jitter (simulates sensor noise)
- Alerts: auto-generated when any stand crosses 0.7 heat threshold or when the simulation is in a period break window
- Flow arrows: static concourse flow data (hardcoded direction + intensity derived from neighboring section heat)

This is the **only new file** that generates fake data. Everything else consumes it through the existing React state flow. When Mark's real ingestion layer ships, this file gets deleted and replaced with the WebSocket subscriber.

## Step 3: Add staff/fan view toggle to page layout

**File:** `src/app/page.tsx`

- Add a `viewRole` state: `'fan' | 'staff'`
- Render a toggle in the header (next to ThemeToggle) that switches between "Fan View" and "Staff View"
- When `viewRole === 'staff'`, the `handleUpdate` callback also runs the mock derivation from Step 2 to produce `StaffViewState`, stored in a new `useRef`
- The existing fan view renders unchanged when `viewRole === 'fan'`
- When `viewRole === 'staff'`, render the staff layout (Steps 4-7) instead of the current fan layout

No changes to `SimulationEngine` — it still produces the same `HeatState`. The staff view is a different rendering of the same data plus derived fields.

## Step 4: Modify ArenaMap for staff mode

**File:** `src/components/ArenaMap.tsx`

Add a `staffMode` prop (optional, defaults to false). When true:

- **Wait time badges** replace transaction count badges on each node — show `~Xm` instead of transaction count
- **Queue depth rings** — a second `<circle>` around each node with `strokeWidth` proportional to `queueDepth` (thicker = longer line), using a semi-transparent version of the heat color
- **Concourse flow arrows** — SVG `<path>` elements along the concourse ring with arrowheads, opacity/thickness proportional to flow intensity. These sit between the concourse and bowl layers
- **LIVE indicator** — a pulsing green dot + "LIVE" text in the top-right of the SVG (replaces simulation time display in staff context)

The existing fan-mode rendering stays as-is when `staffMode` is false/undefined. The new elements are additive — just extra SVG layers.

## Step 5: Build AlertPanel component

**File:** `src/components/AlertPanel.tsx` (new)

A sidebar/card component that displays active alerts:

- Sorted by severity (critical first), then recency
- Each alert shows: location name, severity icon, message, timestamp
- Auto-dismisses alerts older than 5 minutes (configurable)
- Visual treatment: red border for critical, amber for warning, on the dark navy card background
- Max 5 visible alerts, with a count badge if more exist

Alerts are generated by the mock layer (Step 2) based on heat thresholds. In production, they'd also come from POS inventory flags and manual staff input.

## Step 6: Build StandRankings component

**File:** `src/components/StandRankings.tsx` (new)

A compact sidebar list showing all 6 stands ranked by current wait time (longest first):

- Each row: rank number, stand name, horizontal bar chart (width = relative wait time), wait time in minutes
- Bar color follows the existing heat gradient (green → red)
- The shortest-wait stand gets a "SEND FANS HERE" tag (gold, matching existing BEST badge style)
- Updates in real-time as simulation runs

This replaces `ConcessionList` in the staff layout — same data, different emphasis (wait time vs. busyness label).

## Step 7: Build StaffLayout wrapper

**File:** `src/components/StaffLayout.tsx` (new)

A responsive two-column layout for the staff view:

- **Left column (60%):** ArenaMap (staff mode) + demand timeline + game clock
- **Right column (40%):** AlertPanel + StandRankings
- **Bottom bar:** Intermission forecast line (static text derived from game progress — e.g., "2nd intermission rush in ~4 min") + suggested action
- Mobile: stacks vertically (map → alerts → rankings)
- Uses the same CSS variables and Royals branding as the fan view

The header ("ArenaPulse Staff View") replaces "Find the shortest line" tagline. Shows a LIVE indicator and the current period/game clock.

## Step 8: Wire it all together in page.tsx

**File:** `src/app/page.tsx`

Final integration:

- Import `StaffLayout`, `AlertPanel`, `StandRankings`
- Import `deriveStaffState` from `staffMock.ts`
- In the `handleUpdate` callback, when `viewRole === 'staff'`, call `deriveStaffState(heat, stats)` and store result
- Conditionally render `StaffLayout` or the existing fan layout based on `viewRole`
- Pass `staffMode={true}` to ArenaMap when in staff view
- The game selector and simulation controls still work in staff mode — they drive the same engine

## What this does NOT include (for Mark's scope)

- WebSocket infrastructure / ingestion service
- Camera/sensor integration
- Real queue depth estimation
- Inventory tracking from POS
- Authentication (staff vs. fan access control)
- Persistent alert storage

Those are backend/infra concerns for the real-time architecture. This plan mocks the frontend so ops staff can react to the UX before any of that is built.
